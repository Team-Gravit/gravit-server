# Facade Convention

- 커스텀 어노테이션 `@Facade` + `@RequiredArgsConstructor`를 사용하라 (`gravit.code.global.annotation.Facade`)
- Facade는 여러 Service를 조합하는 비즈니스 로직을 담당한다
- 단일 Service 호출만 필요한 경우 Facade를 만들지 마라. Controller에서 Service를 직접 주입하라

## 트랜잭션 경계

판정 질문은 하나다.

> **A는 커밋됐는데 B가 실패한 상태를 사용자가 보게 돼도 괜찮은가?**
> 안 괜찮으면 같은 트랜잭션. 괜찮고 나중에 보정할 수 있으면 이벤트.

여기서 두 계층이 나온다.

| 계층 | 정의 | 처리 |
|---|---|---|
| 1. 사실 기록 | 사용자의 한 행위가 만든 사실과, 그것이 없으면 모순이 되는 파생 상태 | 같은 트랜잭션 |
| 2. 보정 가능한 파생 | 보상, 통지, 집계. 실패해도 사실은 유효하고 재시도로 메울 수 있다 | `AFTER_COMMIT` 이벤트 + 재시도 큐 |

### 응답 규칙

- **쓰기 API의 응답에는 그 쓰기로 확정된 사실만 담아라. "현재 상태"는 조회 API로 분리하라**
  응답에 값을 실으면 그 값을 만드는 쓰기가 트랜잭션에 끌려 들어온다. 함께 롤백되어야 해서가 아니라 응답에 필요해서다. 이렇게 생긴 경계는 도메인이 요구한 것이 아니므로 계층으로 인정하지 마라
- **쓰기 응답에 담는 "확정된 사실"의 기본형은 생성된 리소스의 식별자다**

### 부수 규칙

- 경계 밖으로 나갈 수 있는 것은 사전 검증 조회다. 쓰기는 경계 밖으로 나가지 않는다
- 단일 서비스 위임뿐인 Facade 메서드에는 경계를 만들지 마라. 서비스가 이미 갖고 있다. 조회 메서드도 예외가 아니다
- Facade에 경계를 유지하는 근거는 "조회 메서드라서"가 아니다. 아래 둘 중 하나라도 해당할 때만 유지하라
  - 엔티티를 경계 밖으로 반환해 조립하는가 (`open-in-view: false`이므로 경계가 없으면 깨진다)
  - 여러 조회를 하나의 스냅샷으로 읽어야 하는가

### 경계를 만드는 수단

경계를 좁힐 때는 `TransactionTemplate`을 주입해 쓰기 구간만 감싸라.

```java
Long createdId = transactionTemplate.execute(status -> {
    // 함께 커밋되어야 하는 쓰기와 이벤트 발행
});
```

`@Transactional`을 건 전용 빈에 위임하는 방식은 쓰지 마라. 조합이 필요해서가 아니라 프록시 경계를 하나 더 얻으려고 만드는 빈이라, 그 대가로 계층 결합을 만들 값어치가 없다. 컨트롤러가 Facade를 여러 번 호출해 경계를 나누는 방식도 쓰지 마라. 조합 책임이 컨트롤러로 올라가고 무엇이 원자적인지가 호출 순서에 흩어진다.

`TransactionTemplate`은 Spring Boot가 `TransactionManager` 후보가 하나일 때 자동 등록하므로 별도 설정 클래스를 만들지 말고 주입만 하라.

### 어길 수 없는 제약

- `spring.jpa.open-in-view: false`다. 경계 밖에는 영속성 컨텍스트가 없다
- 리스너가 전부 `AFTER_COMMIT`이고 `fallbackExecution`이 없다. **경계 없이 발행한 이벤트는 예외 없이 폐기된다.** 이벤트 발행은 반드시 경계 안에서 하라
- `AFTER_COMMIT` 리스너는 커밋 직후 동기 실행되고, `TransactionTemplate.execute()`는 그 실행까지 끝낸 뒤 반환한다. 예외는 면접 채점 리스너(`InterviewGradingEventListener`)뿐으로, `@Async`가 붙어 실행기 스레드에서 돌고 `execute()`는 작업 제출만 하고 반환한다
- `AFTER_COMMIT` 리스너에서 난 예외는 `invokeAfterCompletion`이 삼켜 호출자에게 닿지 않는다. 비동기 리스너의 제출 거부도 마찬가지다. 리스너가 실패를 스스로 기록해야 한다

### 보상의 실제 성질

계층 2를 "원자적"이라고 적지 마라. 보상은 각각 **독립적으로 커밋되고 독립적으로 재시도된다.** 리그 점수는 `REQUIRES_NEW`라 호출한 쪽이 롤백돼도 남고, 미션과 일일 기록은 리스너가 예외를 삼켜 재시도 큐에 적재하며, 피드는 큐를 거쳐 별도 요청으로 처리된다. 하나가 실패해도 나머지는 진행된다.
