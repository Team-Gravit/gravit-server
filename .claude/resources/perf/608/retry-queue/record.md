## 환경과 데이터

- 로컬 docker `gravit-postgres-bench`(PostgreSQL 15.18, shared_buffers 128MB), `gravit-redis-bench`
- 환경 점검 `X-E-20261113`: AC 전원, pgbench -S 108,928 TPS(직전 대비 +3.1%), 고정 정보 변경 없음
- 시드: 10월 공통 시드(`X-S-*`). M1·M2·M5는 1만, M4 배치는 10만, M3·공지는 100만, M6는 리그 1m S4 템플릿
- 장애 주입: Redis ACL로 기본 유저의 `ZREM`(M1) 또는 `ZADD`(M5)를 막는다. 하네스는 별도 ACL 유저로 적재, 확인하고 끝나면 원복한다(가드). M2는 리스너를 거치지 않고 SQL로 첫 제출 100건을 1시간 전 시각으로 넣는다
- M4 벤치 스텁(제품 jar에 넣지 않고 `loader.path`로만 얹음): FCM 발송 대신 500건마다 1초 대기, 21시 배치 4단계를 cron 대신 기동 60초 뒤 기본 스케줄러에서 한 번 실행

## 판정 기준 (PLAN-608, 실행 전 고정)

- M1, M2, M5: before 100건, after 0건. 결정적 장애 주입이라 1회
- M3(D4): 100만 행에서 대조 1회가 100ms를 넘으면 `lesson_submission (created_at)` 인덱스 추가
- M4: before 지연 max ≈ 배치 소요, after 지연 max ≤ 30초 + 처리 시간. 부속(D3): 100만 명 공지 1건 점유가 5초를 넘으면 후속 이슈
- M6: insert 1회 추가분 기록. ABBA 5회씩, 범위가 겹치지 않을 때만 "차이 있음"

### M3 · 대조 쿼리 비용, D4 (`Q-S-1m`, `Q-P-1m-*` → `query-plan-{n}.txt`)

`lesson_submission` 100만 행(152.7MB), 최근 24시간 1만 행, 지급 기록 997,572행(V52 백필). `LeaguePointGrantQuerySql`의 대조 쿼리를 since/until(24시간 전 ~ 30분 전), LIMIT 500으로 PG 재시작 직후 cold 1회 + warm 5회.

| | 계획 | 읽은 페이지 | warm p50 | cold |
|---|---|---|---|---|
| base (`-0`, PR 그대로) | 병렬 Seq Scan | 49,582 | **34.1ms** (33.5–34.3) | 56.4ms |
| idx (`-1`, `created_at` 인덱스 추가 비교) | Bitmap Index Scan | 39,324 | 21.3ms (21.1–21.9) | 46.8ms |

- 100ms 기준에 크게 못 미쳐 **D4 인덱스는 추가하지 않는다**
- base warm도 디스크 read가 약 1만 페이지다. 테이블(152.7MB)이 shared_buffers(128MB)보다 커서다. 이 쿼리는 10분에 1번이다

### M4 · 21시 배치 중 재시도 처리 지연 (`Q-B-100k-*` → `batch-{n}.txt`, `batch-probes-{n}.csv`)

10만 시드에서 '오늘 학습 안 함' 대상 60,000명(FCM 토큰 보유), 배치 중 LP 재시도 항목을 5초마다 1건 넣고 큐에서 빠질 때까지를 잰다.

| | before | after |
|---|---|---|
| 배치 소요(스레드 `scheduling-1`) | 137.6초 | 136.7초 |
| 배치 전 적재 p50 / max | 26.4 / 163.1초 | 15.5 / 26.1초 |
| **배치 중 적재 p50 / max** | **67.8 / 137.9초** | **15.2 / 29.9초** |
| 배치 뒤 적재 p50 / max | 11.0 / 25.9초 | 13.7 / 28.3초 |

- before는 배치가 기본 스케줄러 스레드 하나를 점유하는 동안 스윕이 멈춰, 배치 중(과 직전) 적재 항목이 배치가 끝난 뒤에 처리된다. 지연 max가 배치 소요와 같다
- after는 스윕이 `retrySweepScheduler`에서 돌아 배치와 무관하게 30초 주기 안에서 처리된다

**계획 이탈: 대상 10만 → 6만 명.** 대상이 65,535명을 넘으면 `FcmTokenRepository.findAndroidTokensByUserIdIn`이 id마다 바인딩을 하나씩 써서 `PreparedStatement can have at most 65,535 parameters`로 '오늘 학습 안 함' 단계 전체가 실패한다(점검 중 97,071명에서 재현, 알림 행은 생기고 푸시는 0건). #608과 무관한 기존 결함이라 대상을 줄여 쟀고, 별도 이슈 후보다.

### M4 부속 · 공지 1건 스윕 점유, D3 (`Q-N-1m-after` → `notice-sweep.txt`)

100만 시드에서 공지 재시도 항목 1건을 스윕이 처리할 때 `INSERT ... SELECT` 점유 시간(pg_stat_activity).

| 회차 | 생성 알림 | INSERT 점유 |
|---|---|---|
| 1 | 970,064 | 3,464ms |
| 2 | 970,064 | 3,763ms |
| 3 | 970,064 | 3,988ms |

중앙값 **3.8초**로 5초 이하라 **D3 후속 이슈는 열지 않는다**. after 기준이며 재시도 전용 스케줄러 스레드 2개 중 하나를 그동안 점유한다.

### M6 · 레슨 제출 HTTP (`Q-W-1m-*`, 비교 화면 `V-Q-W-1m` → `submit-abba-view.txt`)

`POST /api/v1/lessons/results`, 8클라이언트 60초, (유저, 레슨) 쌍 중복 없는 첫 제출, 고정 시드, ABBA 10회(회차 앞 60초 휴식), 에러 0.

| 지표 | before 중앙값 (범위) | after 중앙값 (범위) | 판정 |
|---|---|---|---|
| TPS | 639.5 (635.8–642.6) | 629.7 (628.2–632.9) | **−1.5%**, 차이 있음 |
| p50 | 11.3ms (11.2–11.3) | 11.4ms (11.4–11.4) | +1.3%, 차이 있음 |
| p95 | 16.9ms (16.9–17.4) | 17.4ms (17.1–17.7) | 차이 없음 |
| p99 | 30.4ms (27.1–42.8) | 31.2ms (26.7–34.7) | 차이 없음 |

- 제출 1건마다 `league_point_grant` insert가 1회 늘어난 비용이다. after 회차는 지급 기록 행수가 제출 행수와 같다
- 2회차부터 시작 load average가 5~7이다(직전 회차의 1분 load가 60초 휴식 동안 다 빠지지 않음). ABBA라 두 쪽이 고르게 겪었다
- after r1 max 1,271.6ms는 단일 표본이라 판정에 쓰지 않는다

## 결론

- 장애 주입 세 가지(중복, 미지급, 유실)가 모두 100건 → 0건이다
- 21시 배치 중 재시도 처리 지연 max가 137.9초 → 29.9초로, 배치 길이와 무관해졌다
- 비용: 레슨 제출 TPS −1.5%(p95는 차이 없음, 17ms대), 대조 쿼리 10분마다 34ms
- D3(공지 분리), D4(`created_at` 인덱스) 모두 추가 조치가 필요 없다
- 후속 후보: FCM 토큰 조회 65,535 바인딩 한도 결함
