## 환경과 데이터

- 로컬 docker `gravit-postgres-bench`(PostgreSQL 15.18, shared_buffers 128MB), `gravit-redis-bench`(Redis 7.0, 영속화 꺼짐). 전 회차 AC 전원
- 시드: 10월 공통 시드. M1~M4·M7은 100k(비탈퇴 97,071명), M5·M6은 리그 1m S4 템플릿(비탈퇴 970,064명). 복제 뒤 V52·V53을 적용한다(공통 시드는 Flyway 기록 없이 V50 무렵 스키마)
- 부하는 실제 API `POST /api/v1/lessons/results`(정답률 100% → +20LP)로 건다
- 어긋남 판정: 대상 유저마다 DB `user_league`(리그, LP)와 Redis 리그 키 15개를 Lua 한 번으로 대조해 빠짐 / 다른 리그 / LP 다름 / 중복으로 나눈다

### 장애 주입 (M1, M3, M4): 벤치 스텁

- 스텁 `BenchRankFaultConfig`를 `loader.path`로만 얹어 `LeagueRankingStore` 빈을 JDK 프록시로 감싼다. 제품 jar와 코드는 그대로다. 같은 소스를 before(`put`/`move`/`remove`), after(`place`/`evict`) jar에 각각 컴파일한다
- 요청 스레드(`http-nio-*`)의 직접 반영만 건드린다. 재시도 스윕(`retry-sweep-*`), 대조·유실 감지(`scheduling-*`), 기동 백필은 제품 그대로 돈다
- after는 매시 대조를 끄고(`reconcile-cron=-`) 복구가 재시도로만 일어났는지 본다
- Redis ACL(#608 방식)은 쓰지 않았다. 랭킹 연결과 재시도 큐 연결이 같은 Redis, 같은 사용자라 랭킹 쓰기만 막을 수 없고, "100번째마다"나 "move의 두 번째 명령만" 같은 조건을 표현할 수 없다

## 판정 기준 (PLAN-609, 실행 전 고정)

- M1: before 100건 잔존, after 0건(스윕 1~2회)

- M6: 100만 명 1회 비용과 조회 영향 기록(매시 실행이 감당 가능한지 근거)
- M7: before 앱 재기동 전까지 빈 목록, after 30초 + 재구축 시간 이내

## 결과

### M1 · 일시 실패 뒤 어긋남 (`S-M1-*` → `fault-injection.txt`)

- 10,000명이 1회씩 제출(+20LP, 리그 그대로), 요청 스레드 쓰기 100번째마다 실패 주입

| | before (`-run3`) | after |
|---|---|---|
| 주입 | 100건 | 100건 |
| 부하 직후 어긋남 | 100명 (LP 다름) | 100명 (LP 다름, 재시도 큐 100건) |
| 관찰 끝 | **100명** (150.8초) | **0명** (부하 끝 10.7초 뒤, 스윕 1회) |
| Redis 인원 / DB | 97,071 / 97,071 | 97,071 / 97,071 |

before는 인원이 DB와 같아 기존 기동 시 인원 대조(`rebuildIfStale`)로도 찾지 못한다. 앱을 재기동해도 남는다.

### M2 · Redis 장애 뒤 어긋남 (`S-M2-*` → `redis-outage.txt`)

- 8워커 0.1초 간격 1인 1회 제출. 20초 → Redis `SHUTDOWN SAVE` 후 60초 정지 → `docker start`(RDB 로드, 데이터 유지) → 20초. after는 대조 cron을 1분으로 덮어썼다

| | before | after |
|---|---|---|
| 요청(장애 전 / 정지 중 / 재기동 뒤) | 1,208 / 3,151 / 1,223, 전부 201 | 1,200 / **8** / 1,096, 전부 201 |
| 정지 중 응답 max | 60,022.8ms (1건) | **60,135.7ms (8건 전부)** |
| 재기동 직후 어긋남 | 3,406명 | 136명 (재시도 적재도 136건 실패) |
| 결과 | 180.8초 동안 그대로 | 대조 1회(97,071명 확인, 반영 136, 523ms) → **재기동 61.1초 뒤 0** |

- 두 실행은 장애 구간 처리량이 달라 어긋남 건수를 비교하지 않는다. 운영 최악값은 1시간 + 대조 소요다
- ⚠️ **발견**: after의 정지 구간 요청 8건이 모두 약 60초 걸렸다. 랭킹 반영이 실패하면 `LeagueRankSyncListener.queueRankSyncRetry` → `RedisRetryEventPublisher.publish`로 재시도 큐에 적재하는데, 이 적재는 타임아웃을 정하지 않은 기본 Redis 연결(Lettuce 기본 60초)을 쓰고 AFTER_COMMIT 리스너, 즉 요청 스레드에서 돈다. Redis가 응답 없이 멈춘 순간(`SHUTDOWN SAVE`의 RDB 저장 중) 보낸 적재 명령이 타임아웃까지 기다렸다. before는 요청 경로에 기본 연결 호출이 없어 1건만 묶였다
- 결정(2026-11-14): #609에서는 고치지 않는다. 기본 연결 타임아웃은 #613 STEP 1(명령 타임아웃 1초 + 끊긴 동안 명령 즉시 거절)의 범위이고, 같은 기본 연결을 쓰는 소셜 피드 재시도 적재도 이번 장애에서 실패했다(before 753줄, after 145줄). PLAN-613 F4에 이 리스너를 추가한다

### M3 · 순서 역전 (`S-M3-*` → `fault-injection.txt`)

- 100명이 레슨 1(+20) 제출 → 1초 뒤 레슨 2(+40). 스텁이 유저별 첫 반영을 3,000ms 늦춰 +40 반영 뒤에 +20 반영이 도착하게 한다(가드: 순서 역전 성립 100명)

| | before (`-run2`) | after |
|---|---|---|
| 부하 직후 어긋남 | **100명** (Redis +20, DB +40) | **0명** |
| 관찰 끝 | 100명 (150.3초) | 0명, 재시도 불필요 |

after는 `place`가 더 큰 점수가 이미 있으면 건너뛰어 늦은 반영이 아무것도 바꾸지 않았다.

### M4 · 리그 이동 부분 실패 (`S-M4-*` → `fault-injection.txt`)

- 100명의 LP를 리그 상한 − 9로 맞춘 뒤 제출 → 전원 승급. before는 `move`의 `remove(from)`만 실행하고 실패(두 번째 명령 실패 재현). after는 이동이 Lua 1회라 두 번째 명령이 없어, 같은 장애를 `place` 스크립트 실행 전 실패로 주입했다

| | before | after |
|---|---|---|
| 부하 직후 | **빠짐 100명** | 이전 리그 100명, 빠짐 0 |
| 관찰 중 빠진 유저 최대 | 100명 | **0명** |
| 관찰 끝 | 빠짐 100명 (151.0초) | 0명 (부하 끝 26.0초 뒤, 스윕 1회) |
| Redis 인원 / DB | 96,971 / 97,071 | 97,071 / 97,071 |

before는 인원이 달라져 앱을 재기동하면 기존 인원 대조로 복구되지만, 재기동 전까지 빠진 채로 남는다.

### M5 · 쓰기 비용 (`S-W-1m-*`, `V-S-W-1m` → `submit-abba-view.txt`)

- 리그 1m S4 복제, 8클라이언트 60초, 워밍업 400건, 같은 요청 순서(해시 가드), 회차 앞 60초 휴식, ABBA 10회. after는 매시 대조를 껐다

| 지표 | before 범위 (중앙값) | after 범위 (중앙값) | 판정 |
|---|---|---|---|
| TPS | 502.1–602.1 (569.0) | 570.7–597.2 (583.0) | 차이 없음 |
| p50 | 11.7–13.2ms (12.1) | 11.8–12.0ms (11.9) | 차이 없음 |
| p95 | 17.4–24.2ms (**18.9**) | 17.5–20.2ms (**18.0**) | 차이 없음 |
| p99 | 28.1–55.4ms (36.7) | 29.3–41.3ms (33.1) | 차이 없음 |

반영이 `move`(왕복 1~2회)에서 `place`(Lua 1회, 키 15개 검사)로 바뀌었지만 제출 비용은 늘지 않았다. 10회 모두 가드 통과(201 외 0, 앱 ERROR 0, LP 증가 = 20 × 성공, 재시도 큐 0, Redis 인원 = DB). 시작 load average 4.5~11로 높았고 ABBA라 두 구성이 고르게 겪었다.

### M6 · 정기 대조 비용 (`S-M6-1m-after` → `reconcile-cost.txt`, `reconcile-cost.csv`)

- 리그 1m S4 복제(비탈퇴 970,064명), 대조 cron 1분, 단계마다 3회. 1%는 LP ≥ 1이고 `user_id % 100 = 0`인 유저의 Redis 점수를 LP−1로 낮춘다

| 단계 | 소요 중앙값 (범위) | 반영 | DB blks_hit | DB blks_read | Redis CPU | 앱 CPU |
|---|---|---|---|---|---|---|
| 어긋남 0, 부하 없음 | **4,110ms** (3,973–4,205) | 0 | 3,912,176 | 34,103 | 0.8초 | 1.5초 |
| 어긋남 1%, 부하 없음 | **8,230ms** (8,170–8,356) | 9,651 | 4,002,609 | 41,467 | 1.2초 | 2.0초 |
| 어긋남 0, 조회 부하 중 | 5,074ms (5,001–5,323) | 0 | 4,699,238* | 179,662* | 1.3초* | 7.5초* |

| 조회 (V-R-H 혼합 8클라이언트, 200) | 요청 | p50 | p95 | p99 |
