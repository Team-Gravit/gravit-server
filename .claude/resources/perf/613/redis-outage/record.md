## 환경과 데이터

- 로컬 docker `gravit-postgres-bench`(PostgreSQL 15.18, shared_buffers 128MB, 병렬 2), `gravit-redis-bench`(Redis 7.0). 전 회차 AC 전원. 호스트 load average는 회차마다 대장에 남겼다
- **Hikari 최대 풀을 운영 기본값 10으로 덮어쓴다.** 벤치 공통 설정(60)은 장애 영향을 작게 보이게 한다
- 시드: M0·M1·M2는 100k(비탈퇴 97,071명), M3·M4는 리그 1m S4 템플릿(비탈퇴 970,064명). 복제 뒤 V52·V53을 적용한다
- 장애 주입
  - `stop`: `docker stop -t 0`. 프로세스가 죽어 연결이 RST로 바로 끊긴다
  - `pause`: `docker pause`. 프로세스가 응답 없이 멈춘다(네트워크 단절, 호스트 멈춤과 같은 모양). 연결은 끊기지 않는다
- M5만 벤치 Redis와 별개인 일회용 컨테이너를 쓴다. 운영 compose와 같은 이미지(`redis:latest`, 로컬 8.8.0), 메모리 제한 768M, 같은 `redis-server` 옵션

### 하네스 주의

- 벤치 Redis는 재시작할 때 `/data/dump.rdb`(11-14 06:22, #609 측정의 `SHUTDOWN SAVE`)를 읽는다. `docker stop` 뒤 복구하면 예전 측정의 키(랭킹, 재시도 큐)가 되살아난다. M2는 이 때문에 3회가 무효였고, 주입 직전 `SAVE` 가드를 더해 4회차를 쓴다. M0·M3·M4는 복구 뒤를 재지 않아 영향이 없다. M1의 '복구 뒤' 구간에는 예전 재시도 큐 항목이 처리됐을 수 있지만, 그 구간 수치는 before·after 모두 정상 구간과 같은 수준이다
- M3의 "DB active"(`R-M3-1m-before`)는 PG 병렬 워커까지 센 값이라 풀 10보다 크다. M4를 재면서 앱 연결(client backend)만 센 값과, 그중 랭킹 폴백 SQL을 실행 중인 수를 더했다. 비교는 같은 지표로 다시 잰 `R-M3-1m-before-run3` ↔ `R-M4-1m-after-run3`이다

| 정상 | 189.2 / 14.2 / 11.6ms (200) | 194.4 / 11.9 / 9.4ms (200) | 25.4 / 4.5 / 4.3ms (401) | 21.0 / 4.5 / 3.6ms (401) |
| stop | **60,043.5** / 12.2 / 9.4ms (400) | **14.7 / 9.3 / 8.4ms (200)** | 5.7 / 3.4 / 3.1ms (400) | 7.5 / 2.6 / 2.0ms (400) |

- 토큰 재발급은 저장소가 Redis뿐이라 여전히 실패한다(범위 밖). 응답 코드 400 `DB_4001`은 후속 이슈 후보다(`GlobalExceptionHandler`가 `DataAccessException`을 400으로 바꾼다)

## M1 · 혼합 부하 중 Redis 60초 장애

`bench.sh outage m1 --variant {before,after} --mode {stop,pause}` · 원문 `m1-unrelated-api.txt` · 구간별 수치 `m1-phases.csv`

부하(닫힌 루프): 무관한 API `GET /api/v1/chapters` 4클라이언트(간격 50ms), 리그 홈 12클라이언트(간격 200ms, `@Transactional` 안에서 Redis 조회), 레슨 제출 2클라이언트(간격 100ms). 정상 30초 → 장애 60초 → 복구 뒤 40초. 구간은 요청을 보낸 시각으로 나눈다.

| 장애 | API | 정상 구간 p95 (before / after) | 장애 구간 before | 장애 구간 after |
|---|---|---|---|---|
| stop | 무관(챕터 목록) | 12.4 / 13.2ms | 16건 · p50 29,845.6ms · p95 30,040.3ms · 오류 25.0% | **3,841건 · p50 5.1ms · p95 14.0ms · 오류 0%** |
| stop | 리그 홈 | 16.4 / 15.6ms | 12건 전부 400 · 60,013.3ms | 3,384건 · p95 15.9ms · 오류 0% |
| stop | 레슨 제출 | 34.1 / 32.1ms | 2건 · 60,004.0ms | 944건 · p95 33.8ms · 오류 0% |
| pause | 무관(챕터 목록) | 12.8 / 13.2ms | 16건 · p50 29,884.6ms · p95 30,025.0ms · 오류 25.0% | **550건 · p50 297.8ms · p95 853.7ms · 오류 0%** |
| pause | 리그 홈 | 14.6 / 13.5ms | 17건 · p95 60,011.8ms · 오류 70.6% | 454건 · p50 1,452.6ms · 오류 0% |
| pause | 레슨 제출 | 34.9 / 34.9ms | 2건 · p50 60,017.3ms | 52건 · p50 1,987.1ms · 오류 0% |

| 장애 | Hikari active / pending 최대 (장애 구간) before | after |
|---|---|---|
| stop | 10 / 9 | 5 / 0 |
| pause | 10 / 10 | 10 / 10 |

- before: 리그 홈이 커넥션을 쥔 채 60초씩 묶여 풀 10이 바닥났다. Redis와 무관한 챕터 API는 60초 동안 16건만 처리됐고 4건이 커넥션을 30초 기다리다 실패했다(403 응답, 앱 요청 로그에는 남지 않음). stop은 복구 뒤에도 Lettuce 재연결을 기다리는 약 19초 동안 리그 홈이 400을 냈다(복구 뒤 구간 오류 47.4%)
- after stop: 무관한 API가 정상 구간과 같은 수준(p95 13.2 → 14.0ms)이다. **목표 달성**
- after pause: 무관한 API 오류 25% → 0%, p50 29.9초 → 0.3초로 회복했지만 **정상 수준은 아니다(p95 853.7ms, 목표 미달).** 명령마다 타임아웃 1초를 기다리는 동안 리그 홈이 트랜잭션 안에서 커넥션을 쥐어, 리그 홈 12개가 풀 10을 계속 다툰다. 남은 원인은 F5(트랜잭션 안의 Redis 조회)이며 이번 범위에서는 고치지 않는다

## M3 → M4 · 랭킹 DB 폴백 동시 실행

`bench.sh outage m3 --variant before` / `bench.sh outage m4 --variant after` · 원문 `m3-m4-rank-db-fallback.txt` · 단계별 수치 `m3-m4-levels.csv`

리그 1m S4(970,064명), 랭킹 클라이언트(내 순위 50% · 리그 목록 50%) 동시 1/2/4/8/16 단계마다 30초, 같은 시간 무관한 API 2클라이언트. Redis 정상 동시 4 기준 → `docker stop` → 동시 1→16.

| 단계 | 무관 API p95 before → after | 랭킹 폴백 쿼리 최대 before → after | 랭킹 TPS before → after | 랭킹 p95 before → after | 503 거절 (after) | PG CPU before → after |
|---|---|---|---|---|---|---|
| 정상(Redis) 동시 4 | 3.8 → 3.9ms | 0 → 0 | 1,890.3 → 1,872.1 | 3.0 → 3.0ms | 0 | 87 → 84% |
| Redis 정지 동시 1 | 7.9 → 6.5ms | 1 → 1 | 5.2 → 11.2 | 298.4 → 227.0ms | 0 | 106 → 205% |
| Redis 정지 동시 2 | 6.6 → 5.8ms | 2 → 2 | 8.8 → 15.0 | 412.9 → 368.8ms | 0 | 178 → 330% |
| Redis 정지 동시 4 | 4.8 → 4.9ms | 4 → 4 | 16.2 → 24.3 | 497.6 → 471.3ms | 0 | 364 → 627% |
| Redis 정지 동시 8 | 6.9 → 6.5ms | 7 → **4** | 27.8 → 20.0 | 597.8 → 628.7ms | 38,164건 (98.4%) | 688 → 724% |
| Redis 정지 동시 16 | **348.3 → 13.6ms** | 10 → **4** | 30.7 → 17.5 | 868.7 → 730.6ms | 55,837건 (99.1%) | 749 → 692% |

- 벌크헤드 상한(D6 = 4)이 지켜졌다. before는 동시 16에서 랭킹 폴백 쿼리가 풀 10을 다 차지했다
- 동시 16의 무관한 API p95가 348.3 → 13.6ms(약 26배 감소)로 내려갔다. 다만 정상(3.9ms)의 약 3.5배다. 남은 몫은 폴백 쿼리 4개 × 병렬 워커로 PG CPU가 약 700%에 머무는 것과, 503을 받자마자 다시 요청하는 닫힌 부하(앱 CPU 149%)다. 동시 8에서는 6.5ms다
- 503 거절 비율은 실제 사용자 비율이 아니다. 하네스 클라이언트가 대기 없이 바로 재요청한다
- 동시 8·16의 랭킹 TPS가 before보다 낮은 것은 상한 4의 의도된 결과다
- 동시 1~4에서 after의 TPS가 높고 p50이 낮은 것은 랭킹 연결이 끊긴 동안 명령을 즉시 거절하고 브레이커가 저장소 호출을 건너뛰기 때문으로 추정한다(before의 랭킹 연결은 끊긴 동안 명령을 쌓아 두고 타임아웃 100ms를 기다린다)
- D6 근거(`R-M3-1m-before`, 1회차): 동시 4에서 무관 p95 5.4ms(정상의 1.4배)·PG CPU 388%, 8에서 PG CPU 704%, 16에서 무관 p95 383.2ms. 8 → 16의 랭킹 TPS 증가는 10%뿐이다

## M5 · 메모리 상한

`bench.sh outage m5 --variant {before,after}` · 원문 `m5-maxmemory.txt`

`EVAL` 한 번에 `SET` 2만 개 × 값 2,048B를 쓰기 오류나 컨테이너 종료까지 반복한다.

| 항목 | before (maxmemory 없음) | after (384mb, noeviction) |
|---|---|---|
| 멈춘 지점 | used 679.9M / RSS 710.5M 다음 회차 | used 419.8M(상한 402.7M) 다음 회차 |
| 컨테이너 | **종료 · OOMKilled · 종료 코드 137** | **살아 있음** |
| 쓰기 | 연결 끊김 | 거절 "OOM command not allowed when used memory > 'maxmemory'" |
| 읽기 / PING | 불가 | GET 정상 · PONG |

- used_memory가 상한을 약 17M 넘긴 것은 Lua 스크립트 한 번(SET 2만 개, 약 52M)이 시작할 때만 메모리를 검사하기 때문이다. 앱의 단건 명령은 넘치는 양이 작다
- 한계: 앱이 OOM 거절을 HTTP 응답으로 어떻게 내보내는지는 재지 않았다. 운영 compose의 `restart: unless-stopped`로 before가 재시작 뒤 같은 상황을 반복하는지도 재지 않았다

## 남은 것 (후속 후보)

- 응답 없이 멈춘 Redis(pause)에서 리그 홈이 트랜잭션 안에서 Redis를 기다리며 커넥션을 쥔다(F5). 타임아웃 1초 동안 풀을 다툰다. Redis 조회를 트랜잭션 밖으로 빼면 M1 pause가 정상 수준에 가까워질 것으로 본다(측정 안 함)
- Redis 장애 응답이 400 `DB_4001`로 나간다
- 토큰 재발급, 로그인, 메일 인증은 Redis 장애 동안 실패한다(대체 저장소 없음, 계획서 범위 밖)
