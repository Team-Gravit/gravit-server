## 구현 계획

### 1. Flyway (`V31__split_mission_definition_and_user_progress.sql`)

기존 `mission`은 정의와 진행이 섞여 있어 컬럼 단위로 고칠 수 없다. 드롭하고 새로 만든다. 진행 중이던 행은 이관하지 않는다 - 백분율에서 횟수를 역산하면 `33.4` 보정과 300초 상한 탓에 부정확한 행이 생기고, 어차피 매일 자정 재할당되어 유실 범위는 최대 하루치다.

기존 테이블에 FK 제약이 없으므로(`V1`의 `mission.user_id`도 `REFERENCES` 없음) 새 테이블도 같은 방침을 따른다.

```sql
-- V31__split_mission_definition_and_user_progress.sql

-- 1) 정의와 진행을 겸하던 기존 테이블 제거 (진행도는 이관하지 않는다)
DROP TABLE IF EXISTS mission;

-- 2) 미션 정의 테이블: 무엇을 하는 미션인지
CREATE TABLE mission
(
    id                     BIGINT GENERATED BY DEFAULT AS IDENTITY,
    code                   VARCHAR(255) NOT NULL UNIQUE,
    title                  VARCHAR(255) NOT NULL,
    description            VARCHAR(255),
    target_type            VARCHAR(255) NOT NULL CHECK (target_type IN
                                        ('COMPLETE_LESSON', 'PERFECT_LESSON', 'LEARNING_SECONDS', 'FOLLOW_FRIEND')),
    target_value           INTEGER      NOT NULL CHECK (target_value > 0),
    max_progress_per_event INTEGER,
    award_xp               INTEGER      NOT NULL CHECK (award_xp >= 0),
    weight                 INTEGER      NOT NULL CHECK (weight >= 0),
    status                 VARCHAR(255) NOT NULL CHECK (status IN ('ACTIVE', 'INACTIVE')),
    created_at             TIMESTAMP(6),
    updated_at             TIMESTAMP(6),
    PRIMARY KEY (id)
);

-- 3) 유저 진행 테이블: 유저가 어디까지 했는지
--    하루 1건 배정 규칙을 UNIQUE로 강제한다. 중복 배정은 애플리케이션이 아니라 DB가 막는다
CREATE TABLE user_mission
(
    id             BIGINT  GENERATED BY DEFAULT AS IDENTITY,
    user_id        BIGINT  NOT NULL,
    mission_id     BIGINT  NOT NULL,
    assigned_date  DATE    NOT NULL,
    progress_count INTEGER NOT NULL DEFAULT 0,
    completed_at   TIMESTAMP(6),
    created_at     TIMESTAMP(6),
    updated_at     TIMESTAMP(6),
    PRIMARY KEY (id),
    CONSTRAINT uq_user_mission_user_date UNIQUE (user_id, assigned_date)
);

-- 4) 기존 MissionType의 미션 정의를 행으로 시딩
--    학습 15분 미션의 목표를 900초로 바로잡는다 (기존 코드는 14분으로 오기입)
--    max_progress_per_event는 1회 제출당 반영 상한이며 학습 시간 미션에만 적용된다 (기존 하드코딩 300초)
--    created_at/updated_at은 now()로 채운다. BaseEntity를 상속시킨 목적(정의 변경 이력)과 일관되게 시딩 시점을 남긴다
INSERT INTO mission (code, title, target_type, target_value, max_progress_per_event, award_xp, weight, status, created_at, updated_at)
VALUES ('COMPLETE_LESSON_ONE',      '레슨 1개 완료하기',            'COMPLETE_LESSON',  1, NULL, 10, 20, 'ACTIVE', now(), now()),
       ('COMPLETE_LESSONS_TWO',     '레슨 2개 완료하기',            'COMPLETE_LESSON',  2, NULL, 15, 10, 'ACTIVE', now(), now()),
       ('COMPLETE_LESSONS_THREE',   '레슨 3개 완료하기',            'COMPLETE_LESSON',  3, NULL, 20,  5, 'ACTIVE', now(), now()),
       ('PERFECT_LESSON_ONE',       '정답율 100%로 레슨 1개 완료하기', 'PERFECT_LESSON',   1, NULL, 30, 16, 'ACTIVE', now(), now()),
       ('PERFECT_LESSONS_TWO',      '정답율 100%로 레슨 2개 완료하기', 'PERFECT_LESSON',   2, NULL, 35,  8, 'ACTIVE', now(), now()),
       ('PERFECT_LESSONS_THREE',    '정답율 100%로 레슨 3개 완료하기', 'PERFECT_LESSON',   3, NULL, 40,  6, 'ACTIVE', now(), now()),
       ('LEARNING_MINUTES_FIVE',    '학습 5분 완료하기',            'LEARNING_SECONDS', 300, 300, 25, 15, 'ACTIVE', now(), now()),
```

**`title`과 `description`의 역할**: `title`은 유저에게 보이는 문구로, 기존 `MissionType.description`이 담던 값이자 응답의 `missionDescription`이 되는 값이다. `description`은 백오피스에서 미션의 의도를 설명하는 운영자용 부연이며 nullable로 두고 시딩하지 않는다. 응답에 나가지 않는 값을 지금 지어내지 않는다.

**`code`를 남기는 이유**: 응답의 `missionType`이 `COMPLETE_LESSON_ONE` 같은 문자열을 그대로 유지해야 한다(응답 스펙 유지 결정). PK는 시딩 순서에 따라 흔들릴 수 있으므로 안정적인 식별자를 별도 컬럼으로 둔다. 단, **서버 로직은 `code`로 분기하지 않는다** - 분기는 전부 `target_type`이 담당한다.

**`progress_count`의 단위**: `target_value`와 **항상 같은 단위**이며, 그 단위는 `target_type`이 정한다. 완료 판정이 `progress_count >= target_value` 한 줄로 끝나는 이유다.

| target_type | progress_count 단위 | 예시 (target_value) | 진행 경과 |
|---|---|---|---|
| COMPLETE_LESSON | 레슨 개수 | 3 | 0 -> 1 -> 2 -> 3 |
| PERFECT_LESSON | 정답율 100% 레슨 개수 | 2 | 0 -> 1 -> 2 |
| LEARNING_SECONDS | 학습 초 | 900 | 0 -> 300 -> 600 -> 900 |
| FOLLOW_FRIEND | 팔로우 횟수 | 1 | 0 -> 1 |

백분율 저장이 문제였던 건 **저장 시점에 원본이 버려지기 때문**이다. "3개 중 2개"를 `66.8`로 적으면 거기서 "2개"를 복원할 수 없다 - `33.4`는 보정 상수라 나누어떨어지지 않는다. 횟수로 저장하면 원본이 남고 백분율은 응답 시점에 파생된다. 되돌릴 수 없는 변환을 저장이 아니라 출력으로 미루는 것이 이 컬럼의 요지다.

**`version` 컬럼을 두지 않는 이유**: 아래 결정 4 참고. 낙관락이 실제로 막아주던 건 XP 중복 지급 하나뿐인데, 그건 `completed_at` 조건부 UPDATE로 더 정확하게 막힌다.

### 2. Entity

#### 2-1. `MissionTargetType` (신규)

컬럼 매핑용 순수 enum이다. 메서드를 두지 않는다.

```java
public enum MissionTargetType {
    COMPLETE_LESSON,
    PERFECT_LESSON,
    LEARNING_SECONDS,
    FOLLOW_FRIEND
}
```

진행량 계산은 `Mission`이 맡는다. `Mission`이 이미 `targetType`과 `maxProgressPerEvent`를 함께 들고 있어 계산에 필요한 정보가 전부 그쪽에 있고, enum이 `accuracy`나 `learningTime` 같은 이벤트 값을 아는 것도 부자연스럽다. 위임을 한 단계 줄인다.

#### 2-2. `Mission` (재작성)

진행 필드(`progressRate`, `isCompleted`, `userId`, `version`)와 진행 갱신 메서드 6개를 전부 들어낸다. 남는 건 정의와, 정의로부터 파생되는 계산뿐이다.

```java
@Getter
@Entity
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Mission extends BaseEntity {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "code", nullable = false, unique = true)
    private String code;

    @Column(name = "title", nullable = false)
    private String title;

    @Column(name = "description")
    private String description;

    @Enumerated(EnumType.STRING)
    @Column(name = "target_type", nullable = false)
    private MissionTargetType targetType;

    @Column(name = "target_value", nullable = false)
    private int targetValue;

    @Column(name = "max_progress_per_event")
    private Integer maxProgressPerEvent;

    @Column(name = "award_xp", nullable = false)
    private int awardXp;

    @Column(name = "weight", nullable = false)
    private int weight;

    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false)
    private MissionStatus status;
}
```

메서드:

```java
// 레슨 완료 이벤트가 이 미션의 progress_count를 얼마나 올리는가. 해당 없으면 0
public int calculateLessonIncrement(
        int accuracy,
        int learningTime
) {
    int rawProgress = switch (this.targetType) {
        case COMPLETE_LESSON -> 1;
        case PERFECT_LESSON -> accuracy == PERFECT_ACCURACY ? 1 : 0;
        case LEARNING_SECONDS -> learningTime;
        case FOLLOW_FRIEND -> 0;
    };

    return capPerEvent(rawProgress);
}
```

문자열 분기가 사라지는 지점이다. 기존의 `startsWith("COMPLETE_LESSON")` 세 갈래와 `switch (missionType.name())` 세 벌(레슨/정답율/학습시간 증분 계산)이 이 `switch` 하나로 모인다. `switch (this.targetType)`은 enum 상수 자체를 분기하므로 상수명을 바꿔도 컴파일러가 잡고, `default`를 쓰지 않아 상수를 추가하면 컴파일 에러로 드러난다.

- `public int calculateFollowIncrement()` — `targetType == FOLLOW_FRIEND ? 1 : 0`
- `private int capPerEvent(int rawProgress)` — `maxProgressPerEvent`가 null이면 그대로, 아니면 `Math.min`. 기존의 `Math.min(learningTime, 300)` 하드코딩이 이 컬럼으로 대체된다
- `public boolean isAchieved(int progressCount)` — `progressCount >= targetValue`
- `public double calculateProgressRate(int progressCount)` — `Math.min((double) progressCount / targetValue * MAX_RATE, MAX_RATE)`를 소수 첫째 자리로 반올림(`Math.round(rate * 10) / 10.0`, `UserLevel.calculateLevelRate`와 같은 방식)
- `public static Mission create(...)` — 정적 팩토리 + private `@Builder`. 운영 경로에서는 시딩된 행을 읽기만 하지만 컨벤션과 테스트 픽스처를 위해 둔다

상수: `private static final int PERFECT_ACCURACY = 100;`, `private static final double MAX_RATE = 100.0;`

`BaseEntity` 상속은 운영자가 정의를 언제 바꿨는지 남기기 위함이다.

#### 2-3. `UserMission` (신규)

```java
@Getter
@Entity
@Table(name = "user_mission")
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class UserMission extends BaseEntity {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "user_id", nullable = false)
    private long userId;

    @Column(name = "mission_id", nullable = false)
    private long missionId;

    @Column(name = "assigned_date", nullable = false)
    private LocalDate assignedDate;

    @Column(name = "progress_count", nullable = false)
    private int progressCount;

    @Column(name = "completed_at")
    private LocalDateTime completedAt;
}
```

- 연관관계 대신 `missionId` 원시값을 쓴다. 기존 `Mission.userId`가 그랬듯 이 코드베이스는 FK 매핑 없이 id 컬럼을 직접 들고 있다
- **`@Version`을 두지 않는다** (결정 4)
- `public static UserMission assign(long userId, long missionId, LocalDate assignedDate)` — `progressCount = 0`, `completedAt = null`
- `public boolean isCompleted()` — `completedAt != null`. **별도 boolean 컬럼을 두지 않는다.** 완료 여부와 완료 시각이 어긋날 여지를 없앤다
- `public void addProgress(int increment)` — `this.progressCount += increment`

완료 처리(`completed_at` 기록)는 Entity 메서드가 아니라 Repository의 조건부 UPDATE로 한다. 아래 3번 참고.

### 3. Repository

`MissionRepository extends JpaRepository<Mission, Long>`:
- 기존 `findByUserId`, `findAll(Pageable)` + `@Lock(OPTIMISTIC)`, `findMissionSummaryByUserId` **전부 제거**
- `List<Mission> findAllByStatus(MissionStatus status)` — 배정 시 활성 정의 로드. 10건 남짓이라 청크마다 조회해도 부담이 없다

```java
@Query("""
    UPDATE UserMission um
    SET um.completedAt = :now
    WHERE um.id = :id AND um.completedAt IS NULL
""")
int completeIfNotCompleted(
        @Param("id") long id,
        @Param("now") LocalDateTime now
);
```

`findAssignedMission`이 한 번의 조인으로 진행과 정의를 함께 가져온다. 두 엔티티 모두 영속 상태라 진행도 변경이 더티 체킹으로 반영된다.

`insertIfAbsent`가 `ON CONFLICT DO NOTHING`을 쓰는 건 이 코드베이스의 관용구를 따른 것이다 - `LessonSubmissionRepository`, `UserLeagueRepository` 등이 이미 PostgreSQL 전용 `nativeQuery`를 쓰고 있고, 테스트도 전부 Testcontainers + PostgreSQL이라 방언 차이 문제가 없다.

`UserRepository`에 추가 (키셋 페이징 - `OFFSET`은 배정 중 유저가 늘거나 줄면 건너뛰기가 생긴다):

```java
@Query("""
    SELECT u.id
    FROM User u
    WHERE u.id > :lastId
    ORDER BY u.id
""")
List<Long> findIdsAfter(
        @Param("lastId") long lastId,
        Pageable pageable
);
```

`User`의 `@SQLRestriction("deleted_at IS NULL")`이 적용되어 탈퇴 유저는 자동 제외된다.

### 4. Service

#### 4-1. `MissionService` (재작성, 배정 포함)

**Service를 쪼개지 않는다.** 별도 `MissionAssignmentService`를 두려던 유일한 이유는 조회 폴백의 `REQUIRES_NEW` 격리였고(자기 호출은 프록시를 타지 않으므로 빈이 갈라져야 했다), 그 격리가 필요했던 이유는 UNIQUE 위반 예외가 호출자의 트랜잭션까지 오염시키기 때문이었다. `insertIfAbsent`의 `ON CONFLICT DO NOTHING`이 **예외 자체를 없애면서** 격리도, 빈 분리도, `try-catch`도 함께 사라진다.

의존성: `LessonSubmissionQueryService`, `MissionRepository`, `UserMissionRepository`, `UserRepository`, `WeightedMissionPicker`, `Clock`

`Clock`은 `TimeConfig`가 KST로 제공하는 빈을 주입한다(`SeasonBatchService`와 동일). `LocalDate.now()`를 직접 부르면 서버 타임존에 끌려가고 테스트에서 날짜를 고정할 수 없다.

```java
@Transactional
public MissionDetailResponse getMissionDetail(long userId) {
    LocalDate today = LocalDate.now(clock);

    // 오늘자 배정이 없으면 조회 시점에 채운다 (자정 배정 누락 안전망)
    // 동시 요청이 먼저 넣었어도 ON CONFLICT가 조용히 넘기므로 재조회 한 번이면 충분하다
    AssignedMission assigned = userMissionRepository.findAssignedMission(userId, today)
            .orElseGet(() -> {
                assignToday(userId, today);
                return findTodayMission(userId);
            });

    return MissionDetailResponse.of(assigned.mission(), assigned.userMission());
}

// 오늘자 UserMission을 삽입한다. 이미 있으면 아무 일도 일어나지 않는다
private void assignToday(
        long userId,
        LocalDate assignedDate
) {
    List<Mission> activeMissions = missionRepository.findAllByStatus(MissionStatus.ACTIVE);
    Mission picked = weightedMissionPicker.pick(activeMissions);

    userMissionRepository.insertIfAbsent(
            userId,
            picked.getId(),
            assignedDate,
            LocalDateTime.now(clock)
    );
}

@Transactional
public void handleLessonMission(
        long userId,
        long lessonId,
        int learningTime,
        int accuracy
) {
    AssignedMission assigned = findTodayMission(userId);
    UserMission userMission = assigned.userMission();
    Mission mission = assigned.mission();

    if (userMission.isCompleted())
        return;

    if (lessonSubmissionQueryService.getLessonSubmissionTryCount(userId, lessonId) > 1)
        return;

    int increment = mission.calculateLessonIncrement(accuracy, learningTime);
    if (increment == 0)
        return;

    userMission.addProgress(increment);

    completeIfAchieved(userMission, mission);
}

// 목표를 채웠고, 아직 아무도 완료 처리하지 않았을 때만 XP를 지급한다
private void completeIfAchieved(
        UserMission userMission,
        Mission mission
) {
    if (!mission.isAchieved(userMission.getProgressCount()))
        return;

    // 조건부 UPDATE가 1을 반환한 트랜잭션만 XP를 지급한다. 동시 완료 시 두 번 나가지 않는다
    int completed = userMissionRepository.completeIfNotCompleted(
            userMission.getId(),
            LocalDateTime.now(clock)
    );
    if (completed == 0)
        return;

    awardMissionXp(userMission.getUserId(), mission.getAwardXp());
}

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void handleFollowMission(FollowMissionEvent followMissionDto) { ... }

@Transactional
public void createMission(long userId) {          // 온보딩 시 오늘자 UserMission 배정
    assignToday(userId, LocalDate.now(clock));
}

@Transactional
public long assignChunk(                          // 자정 스케줄러가 청크 단위로 호출
        LocalDate assignedDate,
        long lastUserId,
        int chunkSize
) { ... }
```

- `private AssignedMission findTodayMission(long userId)` — `findAssignedMission(userId, LocalDate.now(clock))`, 없으면 `MISSION_NOT_FOUND`. **진행 갱신 경로에는 폴백을 걸지 않는다.** 배정이 없는 상태에서 레슨 이벤트가 들어왔다면 진행도 0인 새 미션을 만들어 봐야 그 이벤트에 대한 진행이 유실되고, 조회 경로가 이미 안전망을 갖고 있으므로 여기서는 기존대로 예외를 올린다
- `createMission`은 **이름을 바꾸지 않는다**. `MissionEventListener`가 호출하는 메서드라 시그니처를 유지하면 리스너를 건드리지 않아도 된다
- `getMissionSummary`와 `MissionSummaryResponse`는 제거한다 (결정 3)
- `getMissionDetail`은 **`readOnly = true`가 아니다.** 폴백 배정이 쓰기를 하기 때문이다. 정상 경로(오늘자 행이 이미 있음)는 기존과 동일하게 조인 조회 한 번으로 끝난다
- 같은 이유로 **`UserFacade.getMainPage`의 `readOnly = true`를 제거한다.** `getMissionDetail`이 이 read-only 트랜잭션에 참여하므로 폴백 `INSERT`가 PostgreSQL에서 `cannot execute INSERT in a read-only transaction`으로 거부되고, 안전망이 필요한 바로 그 상황(자정 배정 누락)에 deprecated 메인 페이지 API가 500을 낸다. 위젯 API(`MainPageController.getMission`)는 Service 직접 호출이라 무관하다

`completeIfNotCompleted`가 `@Modifying(clearAutomatically = true)`라 영속성 컨텍스트가 비워진다. 따라서 `completeIfAchieved` **호출 이후에는 `userMission` 인스턴스를 다시 쓰지 않는다.** `addProgress`로 올린 진행도는 이 UPDATE 전에 flush되어야 하므로 `completeIfNotCompleted`에 `flushAutomatically = true`도 함께 건다.

`handleFollowMission`은 기존의 완료 여부 확인 -> 타입 확인 -> 진행 -> XP 지급 순서를 그대로 두되, 타입 확인이 `name().equals("FOLLOW_NEW_FRIEND")`에서 `mission.calculateFollowIncrement() == 0` 판정으로 바뀐다. 기존에는 완료 판정 없이 무조건 XP를 지급했는데, 새 코드는 `completeIfAchieved`를 거치므로 `targetValue`를 채웠을 때만 지급한다. 팔로우 미션의 `targetValue`는 1이라 동작은 같다.

#### 4-2. `assignChunk` (자정 배정)

1. `userRepository.findIdsAfter(lastUserId, PageRequest.of(0, chunkSize))` — 비면 `lastUserId`를 그대로 반환해 루프 종료 신호로 쓴다
2. `userMissionRepository.findAssignedUserIds(assignedDate, userIds)`로 이미 배정된 유저를 걸러낸다 (재실행 멱등성)
3. `missionRepository.findAllByStatus(ACTIVE)`로 정의를 한 번 읽고, 남은 유저마다 `weightedMissionPicker.pick(...)`
4. 유저별로 `insertIfAbsent` 호출. 온보딩이나 조회 폴백과 경합해도 `ON CONFLICT`가 조용히 넘긴다
5. 마지막 유저 id 반환

**트랜잭션 경계가 핵심이다.** 루프는 트랜잭션 없는 `MissionScheduler`가 돌고, `assignChunk` 한 번이 트랜잭션 하나다. 전체 유저를 한 트랜잭션에 묶던 기존 구조와 달리 트랜잭션 길이가 유저 수와 무관하게 `chunkSize`로 고정된다. 자기 호출은 프록시를 타지 않으므로 루프와 청크 처리는 반드시 다른 빈에 있어야 한다 - 여기서는 `@Component`인 스케줄러가 그 역할을 하므로 Service를 하나 더 만들 필요가 없다.

배정 결과는 청크마다 `log.info`로 남긴다 (조회한 유저 수, 신규 삽입 수, 마지막 유저 id). 자정 배정이 실패했는지, 애초에 돌기는 했는지를 사후에 확인할 수단이 지금은 전혀 없다.

청크 크기는 스케줄러의 `private static final int CHUNK_SIZE = 500;`으로 둔다. 청크 처리 중 예외가 나면 스케줄러 루프는 `log.error`를 남기고 **중단**한다 - 실패한 청크의 마지막 유저 id를 알 수 없어 같은 청크를 재시도하는 무한 루프가 될 수 있고, 배정받지 못한 유저는 조회 폴백이 채워준다.

기존 `RandomMissionGenerator`는 호출마다 가중치 합만큼(현재 100개) `ArrayList`를 채운 뒤 하나를 뽑았다. 청크 500명이면 500번 반복된다. 누적 가중치를 한 번 훑으며 `random.nextInt(totalWeight)` 하나로 고르는 방식으로 바꿔 할당을 없앤다. 빈 목록이나 가중치 합 0이면 `RestApiException(MISSION_NOT_FOUND)`.

새 Facade는 불필요 - 미션 배정과 진행은 단일 도메인 로직이다. `MissionService`가 XP 지급을 위해 `UserRepository`를 참조하는 구조는 기존 그대로 유지한다 (아래 결정 2).

## 결정 완료 (Decisions)

- [x] **1. 미션 배정 실패 시 폴백 -> 스케줄러 유지 + 조회 시 지연 배정 폴백**

  먼저 배정이 실패하는 경로를 정리하면 네 가지다. (1) 자정에 배포나 재시작이 겹쳐 스케줄러가 **아예 실행되지 않음**, (2) 인스턴스를 늘렸을 때 조율 장치가 없어 아무도 안 돌거나 중복 실행, (3) 특정 청크의 DB 타임아웃이나 커넥션 고갈, (4) 자정 직후 온보딩과 경합.

  검토한 대안은 두 가지였다.

  **레디스 실패 로그 + 재처리 배치잡**은 (3)만 막는다. (1)과 (2)에서는 실패를 기록할 코드 자체가 실행되지 않으므로 레디스에 아무것도 남지 않고, 따라서 재처리 배치잡도 복구할 대상을 모른다. 가장 흔한 장애 모드를 못 막는 셈이다. 게다가 복구 장치가 레디스 의존성과 두 번째 스케줄러를 새로 끌고 들어와, 원본보다 실패 지점이 많아진다. 복구 경로가 원본보다 복잡해지는 건 나쁜 신호다.

  **조회 시 폴백 배정**은 실패 원인을 묻지 않는다. "오늘자 행이 없다"는 **상태**만 보고 채우므로 (1)~(4)가 전부 같은 경로로 복구된다. 새 인프라 의존성이 없고, 동시 삽입은 이미 넣기로 한 `UNIQUE (user_id, assigned_date)`가 막아준다. 복구 코드가 이미 존재하는 제약 하나에 올라탄다.

  따라서 **B안**을 택한다. 스케줄러는 정상 경로로 남긴다 - 이력이 "받은 날" 기준으로 정확해야 하고, 미접속 유저의 배정도 남아야 하기 때문이다(C안을 택하지 않은 이유). 폴백은 어디까지나 안전망이다.

  덧붙여, 지금은 **자정 배정이 실패했는지 성공했는지 확인할 수단이 아예 없다.** 복구는 폴백이 맡되 관측은 별개 문제이므로 `assignChunk`에 청크별 결과 로그를 남긴다(4-1 참고). 레디스 재처리 큐는 이 로그로 실제 실패 빈도를 확인한 뒤에 필요하면 논의한다.

- [x] **2. XP 지급 경로 -> 현행 유지**

  `MissionService`가 `UserRepository`를 직접 참조하는 구조를 그대로 둔다. 이번 이슈는 스키마 개편에 집중하고, 도메인 경계 정리는 별도 작업으로 분리한다.

- [x] **3. `getMissionSummary` -> 메서드와 DTO 모두 삭제**

  프로덕션 호출부가 없고 테스트 2곳에서만 쓰이는 사장 코드다. `MissionSummaryResponse`도 이 메서드 전용이라 함께 지운다. `MissionRepository.findMissionSummaryByUserId`도 같이 사라진다.

- [x] **4. `UserMission`의 `@Version` -> 두지 않는다. 완료 처리를 조건부 UPDATE로 바꾼다**

  기존 `Mission`에 있던 `@Version`을 그대로 물려받으려 했으나, 실제로 무엇을 막아주는지 따져보면 두 가지가 갈린다.

  **진행도 유실 방지로는 값어치가 없다.** 낙관락이 없어 lost update가 나든, 낙관락이 `OptimisticLockException`을 던지고 `MissionEventListener`가 그걸 `catch`로 삼키든, 결과는 똑같이 "진행 1건 유실"이다. 예외 경로와 컬럼만 늘어난다.

  **실제 값어치는 XP 중복 지급 차단 한 곳뿐이다.** 레슨 3개 미션에서 2개 완료 상태로 두 레슨을 동시 제출하면 양쪽 다 완료로 판정해 XP가 두 번 나갈 수 있다.

  그런데 그건 낙관락 없이 더 정확하게 막힌다. `UPDATE ... SET completed_at = :now WHERE id = :id AND completed_at IS NULL`의 영향 행 수가 `1`일 때만 XP를 지급하면 된다. 두 번째 트랜잭션은 `0`을 받고 조용히 넘어간다 - 예외도, 재시도도, 롤백도 없다. 낙관락은 충돌을 예외로 알리고 처리를 호출부에 떠넘기는데, 여기서는 "먼저 완료한 쪽이 이긴다"가 정답이라 예외로 만들 이유가 없다.

  `version` 컬럼과 필드를 모두 뺀다.

- [x] **5. 배정 로직을 별도 Service로 분리 -> 분리하지 않는다 (`MissionService` 하나)**

  당초 `MissionAssignmentService`를 두려 했던 이유는 조회 폴백을 `REQUIRES_NEW`로 격리해야 했고(자기 호출은 프록시를 안 타므로 빈이 갈라져야 한다), 격리가 필요했던 이유는 UNIQUE 위반 예외가 호출자의 트랜잭션까지 롤백 전용으로 오염시키기 때문이었다.

  `insertIfAbsent`의 `ON CONFLICT DO NOTHING`이 **예외 발생 자체를 없앤다.** 그러면 `REQUIRES_NEW`도, 빈 분리도, `try-catch`도 연쇄적으로 불필요해진다. Service 간 주입을 만들지 않고 `MissionService` 하나로 끝난다.

  청크당 트랜잭션은 여전히 "루프를 도는 빈"과 "청크를 처리하는 빈"이 달라야 하지만, 그 역할은 이미 있는 `MissionScheduler`(`@Component`)가 한다. 스케줄러 -> Service 호출은 Service 간 주입이 아니다.

## 인계 사항 (이번 범위 밖)
- `MissionEventListener`가 세 리스너 모두 `BEFORE_COMMIT` + 기본 전파로 동작해, 미션 처리 중 발생한 예외를 `catch`로 삼켜도 이미 오염된 트랜잭션이 원본 커밋을 되돌릴 수 있다. 리스너 설계는 다른 담당자 몫이라 이번 계획에 넣지 않는다.
- `user_mission`은 유저 수 × 일수로 계속 쌓인다. 지금 규모에서는 문제없지만, 오래된 행의 보존 기간(retention) 정책은 별도 논의가 필요하다.

## Deviation Log
> implement 스킬이 구현 중 계획을 벗어난 지점을 여기에 기록한다. (작성 시점엔 비워둔다)

- `MissionScheduler`: 메서드명 `reassignMission` -> `assignDailyMissions`, `Clock` 주입 추가 — 이유: 계획서가 스케줄러 메서드명을 명시하지 않았고, `assignChunk(assignedDate, ...)` 시그니처상 스케줄러가 KST 기준 오늘 날짜를 만들어야 한다
- `Mission.create(...)`: 파라미터에서 `description` 제외 — 이유: 응답에 나가지 않는 운영자용 nullable 필드라 시딩하지 않는다는 계획 방침과 일관되게, 픽스처용 팩토리에서도 받지 않는다
- `UserMission`: `@Table(uniqueConstraints = @UniqueConstraint(name = "uq_user_mission_user_date", ...))` 추가 — 이유: 테스트는 `flyway.enabled: false` + `ddl-auto: create`라 스키마를 Hibernate가 엔티티에서 생성한다. 엔티티에 복합 UNIQUE 선언이 없으면 테스트 스키마에 제약이 없어 `ON CONFLICT (user_id, assigned_date)`가 "no unique or exclusion constraint matching" 오류로 실패한다. `DailyLearningRecord`가 쓰는 것과 같은 관용구
- `UserCleanDeletionSql`: `DELETE FROM mission WHERE user_id` -> `user_mission` — 이유: 계획의 영향 범위가 `TestUserDataCleanController`만 짚고 이 유저 삭제 SQL을 놓쳤다. `mission`에 `user_id`가 없어져 탈퇴 기능이 `BadSqlGrammarException`으로 깨진다
- 테스트 픽스처 전략: "시딩 행을 `code`로 조회해 쓴다" -> "픽스처가 정의를 직접 저장한다" — 이유: 테스트는 Flyway가 꺼져 있어 시딩 자체가 실행되지 않고, `DatabaseCleaner`가 `pg_tables` 전수 스캔으로 `mission`까지 매번 TRUNCATE 한다. 조회할 시딩 행이 애초에 없다
- `UserServiceIntegrationTest` 온보딩 테스트 2건: 활성 미션 정의 저장 추가 — 이유: `MissionEventListener.createMission`이 활성 정의 없이는 `MISSION_NOT_FOUND`를 던지고, `BEFORE_COMMIT` + 기본 전파라 리스너가 예외를 삼켜도 트랜잭션이 rollback-only로 오염돼 온보딩 전체가 `UnexpectedRollbackException`으로 실패한다 (인계 사항의 리스너 결함이 실제로 발현된 사례)
- `src/test/resources/sql/reset_main_page_ids.sql`: `user_mission` TRUNCATE·IDENTITY RESTART 추가 — 이유: 계획의 영향 범위가 `truncate_all.sql`만 짚었으나 실제로 `@Sql`로 쓰이는 스크립트는 이쪽이다 (`UserFacadeIntegrationTest`, `LearningFacadeIntegrationTest`, `UnitQueryServiceIntegrationTest`). `truncate_all.sql`은 `FriendControllerTest`의 주석 처리된 참조뿐이라 실사용되지 않는다
- `UserRepository.findIdsAfter` -> `findOnboardedIdsAfter` (`u.isOnboarded = true` 조건 추가) — 이유: 계획은 `@SQLRestriction`이 탈퇴 유저를 걸러낸다는 것만 적어 배정 대상 집합이 넓어지는 걸 놓쳤다. 기존 `findAll(Pageable)`은 미션 행이 있는 유저(= 온보딩 완료자)만 돌았는데, 전체 `users` 스캔으로 바꾸면서 가입만 하고 이탈한 유저에게까지 매일 `user_mission` 행이 쌓인다. 관리자는 기존대로 포함한다
