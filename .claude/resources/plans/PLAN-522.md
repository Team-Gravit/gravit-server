# [PLAN-522] 관리자 대시보드 MAU/DAU 추이 데이터 제공

> 이슈: #522
> 브랜치: feat/522-active-user-metrics

## 목표
관리자 대시보드에서 일별 DAU와 월별 MAU 추이를 차트로 볼 수 있게 한다. `User.lastAccessedAt`은 최신 접속 시각만 덮어써 과거 이력이 없으므로, 일자별 활성 이력을 쌓는 `user_daily_activity` 테이블을 추가하고 이를 집계하는 관리자 API 2종을 제공한다.

## 배치 기준
- **쓰기는 user, 읽기는 admin.** 이력을 남기는 주체는 `UserAccessService`이므로 Entity와 쓰기 리포지토리는 `user/`에 둔다. 집계 조회는 관리자 화면 전용이므로 조회 리포지토리와 응답 DTO는 `admin/`에 둔다
- 이 배치는 기존 관행과 같다. `AdminStatsRepository`는 `unit` 도메인의 `Unit` 엔티티를 `admin` 리포지토리로 조회하고, `AdminUserRepository`는 `User`를 조회한다. admin이 다른 도메인 Service를 호출하지 않고 자기 리포지토리로 읽는 방식을 따른다 (`service.md`: 다른 도메인 Service 직접 호출 금지)
- 응답 record는 중첩하지 않고 파일 하나에 하나씩 둔다 (`ChapterStatsResponse`의 중첩 record 방식은 따르지 않는다)
- 쿼리 프로젝션은 `admin/dto/internal/`에 `{Name}Dto`로 둔다 (`dto.md` Internal 규칙)

## 구현 계획

### 1. Entity / Flyway

`V42__add_user_daily_activity.sql`

```sql
-- V42__add_user_daily_activity.sql

-- 일자별 활성 이력 (관리자 대시보드 DAU/MAU 집계용)
-- users.last_accessed_at 은 최신 값만 덮어써 과거 추이를 만들 수 없으므로 별도 이력으로 분리
CREATE TABLE IF NOT EXISTS user_daily_activity
(
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY,
    user_id       BIGINT NOT NULL,
    activity_date DATE   NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT uk_user_daily_activity_date_user
        UNIQUE (activity_date, user_id)
);
```

- FK를 걸지 않는다. 같은 성격의 `daily_learning_record`(V5)도 `user_id BIGINT NOT NULL`만 두고 FK가 없다. FK를 걸면 `CLEAN_USER_DELETION_SQL`의 단일 `WITH ... DELETE`에 이 테이블 삭제를 추가해야 하고, 그러면 과거 DAU/MAU가 소급해서 줄어든다 (결정 필요 1번 참고)
- UNIQUE 컬럼 순서를 `(activity_date, user_id)`로 둔다. 조회는 전부 "기간 내 전체 유저" 집계라 선행 컬럼이 `activity_date`여야 범위 스캔이 인덱스를 탄다. 이 UNIQUE 인덱스 하나가 멱등 insert와 집계 조회를 모두 커버하므로 별도 인덱스를 추가하지 않는다
- 유저별 활동 이력 조회(`WHERE user_id = ?`)는 현재 요구사항에 없다. 생기면 그때 `(user_id)` 인덱스를 추가한다

`UserDailyActivity` Entity - `daily_learning_record`의 `DailyLearningRecord`와 같은 형태

```java
@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@Table(
        name = "user_daily_activity",
        uniqueConstraints = @UniqueConstraint(
                name = "uk_user_daily_activity_date_user",
                columnNames = {"activity_date", "user_id"}
        )
)
public class UserDailyActivity {
    // id (IDENTITY), userId(long, "user_id"), activityDate(LocalDate, "activity_date")
    public static UserDailyActivity create(long userId, LocalDate activityDate)
}
```

- `BaseEntity`를 상속하지 않는다. `activity_date`가 곧 기록 시점이라 `created_at`, `updated_at`이 중복이다 (`DailyLearningRecord`도 상속하지 않는다)
- 정적 팩토리 `create()`는 `common.md`에 따라 두되, 실제 저장은 아래 native insert로 하므로 Entity 저장 경로는 테스트 픽스처에서 주로 쓰인다

### 2. Repository

`UserDailyActivityRepository` (신규, user)

```java
public interface UserDailyActivityRepository extends JpaRepository<UserDailyActivity, Long> {

    @Modifying
    @Query(value = """
            INSERT INTO user_daily_activity (user_id, activity_date)
            VALUES (:userId, :activityDate)
            ON CONFLICT (activity_date, user_id) DO NOTHING
            """, nativeQuery = true)
    int insertIfAbsent(
            @Param("userId") long userId,
            @Param("activityDate") LocalDate activityDate
    );
}
```

- `ON CONFLICT DO NOTHING`으로 멱등하게 만든다. 아래 Service의 "오늘 첫 접속" 판정이 있어 보통은 충돌하지 않지만, 동시 요청과 배포 시점 경계에서 중복 시도가 나올 수 있어 DB에서 막는다
- `clearAutomatically`, `flushAutomatically`는 붙이지 않는다. 같은 트랜잭션에서 이 테이블을 다시 읽지 않으므로 영속성 컨텍스트를 비울 이유가 없다

`AdminActiveUserRepository` (신규, admin)

```java
public interface AdminActiveUserRepository extends JpaRepository<UserDailyActivity, Long> {

    @Query("""
            SELECT new gravit.code.admin.dto.internal.DailyActiveUserCountDto(uda.activityDate, COUNT(uda.userId))
            FROM UserDailyActivity uda
            WHERE uda.activityDate BETWEEN :startDate AND :endDate
            GROUP BY uda.activityDate
            ORDER BY uda.activityDate
    """)
    List<DailyActiveUserCountDto> findDailyActiveUserCounts(
            @Param("startDate") LocalDate startDate,
            @Param("endDate") LocalDate endDate
    );

    @Query("""
            SELECT new gravit.code.admin.dto.internal.MonthlyActiveUserCountDto(
                EXTRACT(YEAR FROM uda.activityDate), EXTRACT(MONTH FROM uda.activityDate), COUNT(DISTINCT uda.userId)
            )
            FROM UserDailyActivity uda
            WHERE uda.activityDate BETWEEN :startDate AND :endDate
            GROUP BY EXTRACT(YEAR FROM uda.activityDate), EXTRACT(MONTH FROM uda.activityDate)
            ORDER BY EXTRACT(YEAR FROM uda.activityDate), EXTRACT(MONTH FROM uda.activityDate)
    """)
    List<MonthlyActiveUserCountDto> findMonthlyActiveUserCounts(
            @Param("startDate") LocalDate startDate,
            @Param("endDate") LocalDate endDate
    );
}
```

- 일별은 `COUNT(uda.userId)`로 충분하다. UNIQUE(activity_date, user_id)가 하루에 유저당 한 행을 보장하므로 이미 distinct 수와 같다
- 월별은 반드시 `COUNT(DISTINCT uda.userId)`다. 한 유저가 한 달에 여러 날 활동하면 여러 행이라 중복 제거가 필요하다
- `EXTRACT`는 Hibernate 6에서 `Integer`를 반환한다. `MonthlyActiveUserCountDto`의 생성자 파라미터를 `Integer, Integer, Long` 래퍼 타입으로 선언해야 생성자 매칭이 실패하지 않는다 (`dto.md` Internal 규칙)
- 구현 중 `EXTRACT` 생성자 매칭이 어긋나면 native 쿼리 + `date_trunc('month', activity_date)::date`로 대체한다. 테스트가 Testcontainers PostgreSQL이라 native로 내려도 검증에 문제가 없다

### 3. Service

`UserAccessService.updateLastAccessed(long userId)` (수정)

```java
@Transactional
public void updateLastAccessed(long userId) {
    LocalDateTime now = LocalDateTime.now(clock);
    LocalDate today = LocalDate.now(clock);

    int updated = userRepository.updateLastAccessedAt(userId, now, today.atStartOfDay());
    if (updated == 0) {
        return;
    }

    userDailyActivityRepository.insertIfAbsent(userId, today);
}
```

- 기존 `updateLastAccessedAt`은 `lastAccessedAt < startOfToday` 조건의 UPDATE라, 반환값 1은 곧 "오늘 첫 요청"이다. 새 판정 쿼리를 추가하지 않고 이 반환값을 그대로 쓴다
- 동시 요청이 들어와도 UPDATE가 행을 잠그고 READ COMMITTED에서 조건을 재검사하므로 한쪽만 1을 반환한다. 이력 insert가 한 번만 일어난다
- 배포 당일에 이미 접속해 `lastAccessedAt`이 갱신된 유저는 그날 이력이 남지 않는다. 배포일 DAU는 과소 집계되며, 이는 이슈에 적힌 "배포 시점부터 축적"의 구체적 의미다

### 7. 전역 예외 핸들러

`GlobalExceptionHandler`에 `ConstraintViolationException` 핸들러를 추가한다.

```java
@ExceptionHandler(ConstraintViolationException.class)
public ResponseEntity<ErrorResponse<List<String>>> handleConstraintViolationException(ConstraintViolationException e) {
    // violation 당 "[ 필드 ][ 메시지 ][ 거부된 값 ]" 형태로 모아 기존 handleExceptionInternal(List<String>) 재사용
    // -> CustomErrorCode.INVALID_PARAMS (400)
}
```

- **이 핸들러가 없으면 `@Min`, `@Max`는 400이 아니라 500을 낸다.** 현재 핸들러에는 `MethodArgumentNotValidException`(`@Valid @RequestBody` 전용)만 있고, `@Validated` 클래스의 `@RequestParam` 제약 위반은 AOP 프록시가 `ConstraintViolationException`을 던져 `@ExceptionHandler(Exception.class)` 폴백(500 `INTERNAL_SERVER_ERROR`)에 잡힌다
- 메시지 조립은 기존 `handleValidException`과 같은 형태로 맞춘다. 응답 코드도 기존 `INVALID_PARAMS`를 그대로 쓰므로 새 `CustomErrorCode`를 추가하지 않는다
- **부수 효과(의도된 것)**: 파라미터 제약이 걸린 기존 엔드포인트도 500에서 400으로 바뀐다. 현재 해당되는 곳은 `MyPageController`의 `year` 파라미터(`@Min(2025) @Max(2099)`)뿐이다. PR 설명에 이 동작 변경을 적는다
